# TofsDevOps — свой сервер, архитектура, разработка

Продолжение [README.ru.md](../README.ru.md) для тех, кто ставит бота на свой сервер или хочет менять код. Установка на Railway по кликам — в [SETUP.md](SETUP.md), возможности — в [FEATURES.md](FEATURES.md).

## Свой сервер (Docker Compose)

Нужны: Docker и токен бота от [@BotFather](https://t.me/BotFather).

Без исходников — готовый образ `ghcr.io/morgunovtech/tofs_devops_bot:latest` (amd64 и arm64), короткий `docker-compose.yml` для него — в [README](../README.ru.md#бесплатно-свой-сервер-через-docker). Ниже — сборка из исходников, для своих правок.

```bash
git clone https://github.com/morgunovtech/Tofs_DevOps_bot.git
cd Tofs_DevOps_bot
cp .env.example .env
# Заполни ОДНО значение: TELEGRAM_BOT_TOKEN (от @BotFather)
APP_COMMIT=$(git rev-parse --short HEAD) docker compose up -d --build
```

Отправь боту `/start` — первый пользователь становится админом, и бот сам
проведёт через добавление первого сайта. Сайты, время отчётов, тихие часы и
heartbeat-джобы управляются из чата; `.env` нужен только для опциональных
интеграций ниже (задокументированы в [.env.example](../.env.example)):

| Что включается | Переменные |
|---|---|
| Виджет, ссылки задач и статус-страница на своём сервере (за reverse proxy с TLS — README, «Публичный адрес на своём сервере») | `PUBLIC_BASE_URL`, `TRUST_PROXY=1` |
| Кнопка передеплоя + автопередеплой | `DEPLOY_HOOKS`, `AUTO_REDEPLOY` |
| Кнопка сброса кэша Cloudflare | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID` |
| Dead-man switch | `HEARTBEAT_JOBS` |
| Статус индексации Google | `GSC_SERVICE_ACCOUNT_FILE`, `GSC_PROPERTY` |
| Статус индексации Яндекса | `YANDEX_WEBMASTER_TOKEN` |
| Скорость у посетителей Chrome (данные Google) | `CRUX_API_KEY` |
| Порядок в GitHub в недельном отчёте | `GITHUB_TOKEN`, `GITHUB_OWNER` (необязательно) |
| Перезапуск контейнеров | `AUTORESTART_CONTAINERS` + монтирование docker.sock (сокет = root на хосте) |
| Очистка диска (висячие образы и кэш сборки старше суток, не чаще раза в 12 ч) | `AUTO_CLEANUP=1` + docker.sock, по умолчанию выключена |
| Внешний сторож | `SELF_HEARTBEAT_URL` |
| Telegram через прокси (сервер в России) | `TELEGRAM_PROXY` |

Поведение, которое меняется только в `.env` (умолчания — из `config.py`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TELEGRAM_ADMIN_USER_ID`, `TELEGRAM_ADMIN_CHAT_ID` | пусто | закрепляют владельца (и группу для тревог); окружение главнее базы |
| `PUBLIC_BASE_URL`, `TRUST_PROXY` | пусто, `0` | публичный адрес за reverse proxy; доверять `X-Forwarded-For` |
| `SECOND_OPINION` | `1` | check-host.net перед тревогой и для порта 25 MX-хостов (выключатель в чате главнее) |
| `REGION_SPEED` | `0` | origin каждого сайта раз в 6 ч уходит на check-host.net ради замера из региона |
| `SCREENSHOT_TEMPLATE` | microlink.io | куда уходят адреса страниц за снимками; `off` — без снимков |
| `AUTO_REDEPLOY` | `1` | дёргать deploy hook при падении сайта (выключатель в чате главнее) |
| `AUTO_CLEANUP` | `0` | с docker.sock: при полном диске удалять висячие образы и кэш сборки старше суток (выключатель в чате главнее) |
| `DISK_ALERT_PCT` | `85` | порог тревоги о диске |
| `ESCALATION_REPEAT_MIN` | `30` | первое напоминание о лежащем сайте; дальше ×2, ×4 … до 4 ч; `0` — без напоминаний |
| `SSL_RENEW_WARN_DAYS` | `10` | «автопродление, похоже, сломалось», если серийник не сменился так близко к сроку |
| `LINKS_CHECK_INTERVAL_HOURS` | `6` | часов между обходами ссылок; `0` — без обхода |
| `RETENTION_DAYS`, `DB_BACKUP_KEEP` | `30`, `7` | сколько дней сырых проверок до ночного сворачивания; сколько ночных копий держать в `data/backups/` |
| `DEPENDENCY_WATCH` | `1` | недельная проверка OSV и ежечасная проверка деплоя |
| `QUIET_HOURS` | пусто | тихих часов нет, пока не заданы здесь или в «🔔 Когда писать» |

## Статус от другого бота

Бот, который отмечается у TofsDevOps (⏰ «Бот или задача по расписанию»), может вместе с отметкой прислать, что он видит, — строки появятся на главном экране, в карточке задачи и в утренней сводке. Тот же адрес отметки, только `POST` с JSON:

```
POST https://<бот>/api/heartbeat/<токен задачи>/<задача>
Content-Type: application/json

{"title": "📣 Соцсети",
 "items": [{"name": "Telegram-канал", "level": "ok", "text": "12 340, +18 за сутки"},
           {"name": "LinkedIn", "level": "warning", "text": "cookie истекает через 3 дн."}],
 "open_url": "https://t.me/social_tracker_bot",
 "heartbeat": true}
```

- Адрес у каждой задачи свой: токен выводится из `HEARTBEAT_SECRET`, и утечка одной строки cron открывает одну задачу, а не все. Точный адрес — в карточке задачи, «🔗 Как подключена». Смена секрета (🔑 в «🔌 Подключениях») меняет адреса всех задач сразу.
- `HEAD` отметкой не считается (проверяльщики ссылок и превью в чатах шлют именно его) — ответ `405`. Имя, которого бот не ждёт, — `404`: опечатка в cron видна сразу, а не тревогой через неделю. Старые адреса с общим секретом (`/api/heartbeat/<HEARTBEAT_SECRET>/<задача>`) продолжают работать, но каждую задачу стоит перевести на её адрес — бот один раз напомнит об этом по каждой.
- `items` — от 1 до 10; `name` до 40 символов, `text` до 120; `level` — `ok` ✅, `warning` 🟠, `critical` 🔴, `unknown` ⚠️.
- `title` (до 40) — заголовок блока; `open_url` (https) — кнопка «↗️ Открыть» на карточке.
- `heartbeat: false` — только обновить строки, не засчитывая отметку: например, проверка каждые 30 минут при ежедневной отметке «сбор прошёл».
- Плохой JSON — `400` с причиной и без отметки: отправитель увидит ошибку в логах, а молчание задачи — тревогой. Статус хранится только для задач, которые TofsDevOps ждёт.
- Строки только показываются: тревоги и подробные экраны остаются у самого бота. Если бот замолчал дольше интервала, вместо его строк — «⚠️ молчит — не знаю, что сейчас»; если отметки идут, а строки он присылал больше интервала назад — «строки устарели».
- Молчание считается от последней отметки или от добавления задачи (что позже) за вычетом простоя самого бота: задача, добавленная в работающий бот, не получает «так и не выходит на связь» на ближайшем тике, а редеплой не делает живую задачу «молчащей» и не прощает мёртвую.

## Архитектура

```
main.py                 точка входа: БД → сервисы → веб-сервер → планировщик → polling
├── monitors/           доступность, ssl, домены (rdap), dns, ссылки, 5xx,
│                       seo/geo, хост — типизированные результаты, общая лестница алертов;
│                       разбор HTML (BeautifulSoup) — в дочернем процессе
│                       monitors.parse_child (parse_worker: старт по требованию,
│                       выход после 60 с простоя), карта сайта — в потоке
├── services/           notifier (все проактивные сообщения идут через него:
│                       приоритеты, mute, тихие часы, паузы), settings, maintenance, secrets,
│                       runtime (админ), updates (контроль зависимостей),
│                       действия Cloudflare, Docker API, скриншоты, GSC, Яндекс,
│                       порядок в GitHub
├── reports/            планировщик (задачи — setup_scheduler), форматтеры, недельный отчёт
├── handlers/           по роутеру на экран за одним AdminFilter
├── web/                aiohttp: API фидбека (CORS только для сайтов из бота,
│                       лимиты по адресу и по сайту, ≤5 сообщений в час в чат +
│                       часовая сводка), heartbeat, статус-страница + JSON
│                       + бейджи, виджет; HTML-шаблон в web/templates
├── db/                 aiosqlite, WAL, миграции через PRAGMA user_version,
│                       ретенция, бэкапы
├── utils/              url/текст/время — общие помощники для всего выше
└── tests/              pytest: чистые функции, БД, мониторы против локального
                        HTTP-сервера, правила notifier, веб-эндпоинты, экраны бота
```

Стек: Python 3.12–3.14 (верхнюю границу задаёт Requires-Python закреплённой версии aiogram, см. `requirements.in`), [aiogram 3](https://github.com/aiogram/aiogram), aiohttp, APScheduler, SQLite (WAL), `zoneinfo` из stdlib. SaaS-мониторинга, в котором надо регистрироваться, нет — бот и *есть* мониторинг; он пользуется бесплатными публичными проверялками, см. README, «Что уходит с вашего сервера». Графических библиотек тоже нет: графики — моноширинный текст.

Всё живёт в одном event loop, поэтому ничего тяжёлого в нём не исполняется. Разбор HTML (SEO-аудит, обход ссылок, подсказка фразы) идёт в дочернем процессе `python -m monitors.parse_child`: `monitors/parse_worker.py` запускает его при первом разборе, передаёт задания по одному кадрами JSON через pipe, убивает при зависании (30 с) и отпускает после 60 с простоя — память уходит вместе с ним. Это не `multiprocessing`: тот заново импортировал бы `main.py`, то есть весь бот, в каждом рабочем процессе; дочерний процесс импортирует только `monitors`. Поток не помог бы — `html.parser` держит GIL. Карта сайта разбирается в потоке (`asyncio.to_thread`: регэксп линейный, `html.unescape` GIL отпускает), картинка карточки отдаётся `web.FileResponse` (sendfile), виджет читается с диска один раз при старте.

Про модель безопасности виджета: «секрет» виджета уезжает каждому посетителю сайта, поэтому endpoint считается публичным — защита строится на rate limiting и жёстких лимитах размера, а не на токене. Именно поэтому у heartbeat-эндпоинта *другой* секрет — всегда: `HEARTBEAT_SECRET`, равный `WEBHOOK_SECRET`, игнорируется, вместо него используется сгенерированный (`services/secrets.py`). Осознанный и задокументированный компромисс для инструмента личного масштаба.

## Разработка

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
pip install --require-hashes --no-deps -r requirements.txt   # ровно то, что в образе
ruff check .          # линтер + порядок импортов
pytest -q             # без сети и без Telegram
pip-audit -r requirements.txt --strict
```

### Зависимости

Прямые версии живут в `requirements.in` (9 пинов `==`). `requirements.txt` —
сгенерированный lock: все 30 пакетов, включая транзитивные, с хешами, собранный
под Python 3.12 (младшая версия матрицы CI). Образ и CI ставят ровно его
(`pip install --require-hashes --no-deps`); тест `test_the_lock_is_compiled_from_requirements_in`
следит, чтобы lock не отстал от `requirements.in`. Поменял пин в `requirements.in` —
пересобери lock:

```bash
python3.12 -m venv /tmp/piptools && /tmp/piptools/bin/pip install pip-tools
/tmp/piptools/bin/pip-compile --generate-hashes --strip-extras --output-file=requirements.txt requirements.in
```

Еженедельный PR Dependabot делает это сам; если он обновил только `requirements.in`,
CI покраснеет и PR подождёт человека — перегенерируй lock в его ветке той же командой.

Аварийный путь: на aiohttp или pydantic вышла уязвимость, а свежую версию не
пускает верхняя граница aiogram. Поставь нужную версию поверх границы —
`uv pip compile requirements.in --generate-hashes --universal --python-version 3.12 --override overrides.txt -o requirements.txt`
(с `--no-deps` pip поставит её, не проверяя границу), прогони полный pytest на
3.12–3.14 и собери образ. Пока ждёшь aiogram, держи в CI
`pip-audit … --ignore-vuln <ID>` с датой пересмотра в комментарии. Цена —
комбинация, которую aiogram не тестировал.

CI (ruff, pytest на Python 3.12, 3.13 и 3.14, `pip-audit --strict` для lock и для дев-инструментов; на ноге 3.13 — сборка образа и его запуск: `id -u` = 10001 и `import main` внутри контейнера, в PR ещё и сборка под arm64) запускается на каждый PR и на push в `main`; зелёный `main` публикует образ в ghcr.io, причём `:latest` получает только прогон самого нового коммита `main` — повторный запуск старого прогона его не откатит. Actions закреплены по SHA коммита, базовый образ — по digest; Dependabot двигает и то и другое. Отдельный шаг «versions aiogram keeps out» предупреждает (не роняя сборку), когда свежий aiohttp или pydantic отрезан верхней границей aiogram. Dependabot по субботам в 13:00 (Europe/Moscow) открывает один сгруппированный PR для библиотек Python, раз в месяц — для базового образа и Actions; версия попадает в PR не раньше чем через 7 дней после выхода (мажорная — через 30). Автомерж сам ждёт все проверки «lint · test · audit» и вливает только патчи и минорные обновления библиотек Python — ровно тот коммит, который проверили тесты; базовый образ, Actions и мажорные версии ждут человека. Настраивать репозиторий не нужно; если нужно правило ветки — требуй «lint · test · audit (3.12)», «(3.13)» и «(3.14)». Контейнер работает от непривилегированного пользователя; `entrypoint.sh` сначала чинит владельца data-тома.
