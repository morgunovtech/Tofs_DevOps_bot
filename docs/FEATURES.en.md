# TofsDevOps — everything it does

The long version of the [README](../README.md): every monitor, every screen, quick start for Railway and Docker Compose, the architecture and the development loop. Russian: [FEATURES.md](FEATURES.md), [SETUP.md](SETUP.md), [WHY.md](WHY.md).

## What it does

### 📡 Monitoring
- **Anti-flap** — an incident opens after 2 planned failures in a row (the threshold is a per-site dial); a single network hiccup never wakes you. Only scheduled checks count toward the threshold: a «🔄 Проверить», a digest snapshot or the re-check after an alert writes its row into the history but cannot bring the alert closer. A site that fails every other check and never makes «N in a row» opens an incident too — once at least half of the last 2×N (at least 6) planned checks failed; the alert says so: «Сбой в 3 из 6 последних проверок». «✅ back up» comes after two planned successes in a row (one when the interval is 30 minutes or longer), and the downtime ends with the first of them. Downtime and uptime are measured in time, not in check rows: a check speaks for the time until the next one, but no longer than the site's interval, so the re-checks after an alert and «🔄 Проверить» do not add an interval each, a changed interval does not re-weigh the past, and the hours the bot itself was down count neither as up nor as down; the average answer time counts answered checks only — a timeout is not a speed. «Лежал N (from–to)» in the recovery message and «не открывается с ЧЧ:ММ» in the alert count from the first failed check of the series, not from the moment the incident opened after N failures; when the site came back while the bot was away, the message says so: «лежал не меньше N; когда именно поднялся — не знаю» with the unchecked span. Down again within 30 minutes after the ✅ — the same incident is reopened instead of ringing and rebuilding anew: one quiet 🟠 «мигает: 3 падения за час» an hour instead, and the ✅ after a flap arrives without a ring.
- **One outage, one message** — three or more sites falling in one tick are ONE ringing alert, «🔴 Не открываются сразу N сайтов» ("N sites down at once — looks like a hosting or network outage"), with «📋 Показать по сайтам» (the numbered list below, an «ℹ️ N» for each) and «🔧 Я чиню все» ("I'm fixing them all": silence for all of them); sites that fall within the next 10 minutes are added to it by an edit, without a new ring, and one or two said on their own just before join the list once there are three. Recoveries («✅ Снова открываются N сайтов») and escalation reminders («🔴 Всё ещё не открываются N сайтов») are grouped the same way. The helpers get the group message like a single «site down» — by the public names. A site on «🔧 Я чиню» or in a maintenance window stays out of the group: its alert waits for the end of the silence as before. So that one outage does not hit the bot in one burst, the checks of one interval are spread over its minutes: the first check after a start comes at once, the next one of every site is moved by its own share of the interval, then each keeps its own step. The bot's screens do not answer «stale» during such a storm: a short Telegram wait (up to 5 s) is waited out, a longer one is said in a pop-up («Telegram asks to wait N s»).
- **Availability** every 5 minutes — with a twist: before paging you, it re-checks from three external nodes (check-host.net) and from the node in your time zone's country, all within 30 seconds. Up for most of them and from your country — no alarm: one quiet 🟠 «down from my server, up from 2 of 3 external nodes» with a hint that visitors in the bot's region probably see the same (a block, a provider, a CDN node), and a ✅ «opens from my server again» once it does. One lucky node out of three does not cancel the alarm: a split is a 🔴 with the honest «opens only from 1 of 3 external nodes — it seems down in places»; down from your country — «opens from outside, but not from Russia». A certificate error never goes to the second opinion — the server answered, every visitor sees the same warning — and pages right after the threshold. While the incident is open the external nodes are not asked again.
- **SSL certificates** — an alert ladder (14 → 7 → 3 → 1 → 0 days) instead of daily nagging, plus a *renewal watch*: it tracks the certificate serial and warns when auto-renewal (Cloudflare/certbot) silently stops working. A renewal that worked is normal operation: no message, just a line in the Sunday report.
- **Domain expiry** via RDAP (the protocol that replaced WHOIS for gTLDs in 2025; IANA bootstrap + rdap.org, a tiny async WHOIS fallback for .ru/.su/.рф), with its own alert ladder. One lookup per domain, on its «carrier» site (the bare domain, else `www.`, else the first by address): every site of the domain sees the expiry, the alert and the incident live on the carrier. A failed lookup (a 429, a timeout, a WHOIS answer without a record) keeps the last known expiry and registrar. The registrable domain follows a suffix list (`co.uk`, `com.kz`, `org.ua`…: a generic second label under a two-letter zone); an address on a platform's domain (`github.io`, `synology.me`, `duckdns.org`, `pages.dev`…) has no domain and no DNS of the owner's to watch — no expiry, no alerts, and the card says so.
- **DNS changes** — snapshots A/AAAA/CNAME (per host of the owner's) and NS/MX (per their domain) hourly; a changed NS record (that's what a hijack looks like) is a critical alert, and so is every MX disappearing (mail stops arriving). A/AAAA behind a rotating pool (a CDN answers with two of its twenty addresses) are not a change: the alert comes when an answer shares none of the addresses seen in 7 days, two consecutive checks in a row. A name that stops answering (SERVFAIL hour after hour — dead NS servers, a DS record left after a change of NS) is said once after three consecutive failed lookups, and the stored baseline stays; the card shows «🔴 DNS: NS-серверы … не отвечают уже N ч». When no name resolves at all, it is the bot's own network — one line in the log, no alert.
- **Speed from the audience's region** — every 6 hours a request from a check-host.net node in the country of your time zone: the card says «за 0.8 с из России» instead of a timing from the bot's data centre. Its own switch, off by default (`REGION_SPEED=1` or «⏱ Скорость из региона» on the «🌐 Вторая точка» screen): the addresses of all sites go to that service, and that is the owner's call. Only the site's origin (`scheme://host[:port]/`) goes there — never a page path or a query. Sites that are down are not timed.
- **What leaves your server for third parties** (`utils/net.py`, `is_private_target` — one rule for all of them) — the bot hands site addresses to four outside services, each of which can be switched off: check-host.net (the second opinion — once, when the failure threshold is reached and before the incident opens; port 25 of the mail servers; the regional timing), the screenshot service (`SCREENSHOT_TEMPLATE`, microlink.io by default; `off` — no screenshots), Google CrUX (only with a key) and RDAP (the zone's registry from IANA's list; rdap.org only when that list itself could not be fetched, and a zone without RDAP is not asked at all). Internal addresses — 10.x, 192.168.x, 127.x, CGNAT, `.local`, `.lan`, `.home`, `.internal`, `.corp`, single-label names — never leave the server for any of them: such a site gets no second opinion, no picture, no CrUX data and no registration date («внутренний адрес — регистрации домена нет»). A public-looking name that resolves to an internal address on the bot's host (`nas.home.example.com → 192.168.1.10`) stays home too — the alert comes «without an outside check». The «🔌 Подключения → 🌐 Вторая точка» screen says what goes where and where each value comes from («из .env (SECOND_OPINION=1)» or «задано здесь, в чате»): a switch in the chat overrides `.env`, and one that matches `.env` is forgotten, so `.env` is the master again.
- **Real visitors' speed** — not the bot's own request: what visitors actually wait for, from Google's Chrome UX Report. Nothing to install on the sites: with a free Google API key the bot asks once a day how soon the page appears (LCP), how soon a tap is answered (INP) and how much the layout jumps (CLS) over 28 days. Small sites often have no data — Google only covers sites with enough Chrome visitors — and the card says so. The card says it in words («страница появляется за 1.8 с, кнопки откликаются за 0.12 с, вёрстка не прыгает · посетители Chrome за 28 дней, данные Google»); slow by Google's yardstick (p75 in the red zone) is one quiet alert with a PageSpeed Insights button.
- **Basic security** — every six hours, what anyone can see from outside: `/.git/HEAD` or `/.env` open to the world (the whole code with its history, or passwords and keys) rings; the content is checked, so a single-page app answering index.html for any path is not a false alarm. Sites on `http://` get the `.git`/`.env` probes too — for them that is all that is checked. A site that still opens over plain `http://` (asked only of https sites without a port of their own), and the four protective headers any site can have safely (HSTS, X-Content-Type-Options, X-Frame-Options or `frame-ancestors`, Referrer-Policy), come as one quiet message with the ready text for the hosting — a `_headers` file for Cloudflare Pages and Netlify, a `vercel.json` block, plain header lines for the rest. CSP is advice only (a wrong one breaks the site). A probe without an answer (a timeout, 429, 5xx, a refused port) is not «the file is gone»: the previous verdict stands and an open 🔴 is never closed by it; a homepage behind a gate (401/403/429/451, a Cloudflare challenge) is not the site, so nothing changes; a silent port 80 counts as closed only after three checks in a row. A new finding inside an open incident (`.env` appearing while `.git` is already open) rings again, with the whole list. «Recheck» on a site that did not answer says so and shows the last check. The public status page never lists these.
- **Your domain's mail** — hourly, for every domain among the sites: who receives the mail (Proton, Google Workspace, Microsoft 365, Yandex 360, Zoho, iCloud, Fastmail, Cloudflare Email Routing…), whether those servers exist and accept connections on port 25 from outside (asked of check-host.net; a control server is asked on the same nodes that reached no MX, so nodes that cannot open port 25 at all are never mistaken for a dead mailbox). Two failed checks ten minutes apart are a critical «your mail does not accept letters» — the recheck is scheduled after a check from the ✉️ screen too. SPF (missing, two records instead of one, `+all`, over ten lookups, the provider left out), DKIM and DMARC problems arrive as one quiet message with the exact record to paste — two SPF records are merged into one for you, `redirect=` becomes `include:`, and every SPF finding shares one corrected record. A new finding inside an open incident (a second SPF record while «no DMARC» is open) is said again, with the whole list. A domain gone from DNS (NXDOMAIN) or MX that vanished is never «mail is fine»: no «✅» — at NXDOMAIN the snapshot and the incidents stay as they were (the DNS and domain checks speak about that), vanished MX close the mail alarms silently (the DNS check rings about them). One domain never holds the others: a check that overruns its budget keeps the last result, and the ✉️ screen says when the check did not happen.
- **Broken links** — a link that does not open is a dead end for your visitor wherever it points, so own and external links are one list. What decides is certainty, not the domain: a 4xx or a vanished domain counts at once, a timeout or 5xx only if the link still fails three hours after the first failure (a crawl after a restart minutes later does not count — a short outage on the far end, like GitHub's, is not a broken link), a bot block (401/403/429, a `cf-mitigated: challenge` page) never; a 503 has to persist. Links are resolved as a browser does (from the page's address after redirects, `<base href>`, no `#fragments`), and the certificate of a foreign link is checked like the site's own. One crawl checks up to 300 links (own site first, at most 50 foreign hosts), the rest in the following crawls (the «🔗 Ссылки» screen says how many of the page it checked); links once found broken are rechecked in every crawl on top of the window, and the problem closes only after the windows have gone a full round without one. At most two requests to a foreign host at a time, 16 foreign requests in flight over all crawls; the names in links are resolved in a separate thread pool, so a silent DNS of someone else's site does not delay the availability checks.
- **Deep 5xx probe** — samples pages from `sitemap.xml` hourly, catching "homepage is fine but half the site is erroring". A page that does not answer within 15 seconds or drops the connection is not "healthy": it counts with the 5xx ("5xx or no answer on 2 of 10 pages", the card says «🔴 /path — не ответила»); when not one sampled page answered there is no verdict — that is the bot's network or the whole site, the availability monitor's call. A vanished sitemap closes an open deep incident quietly, without "✅ all pages answer again": nothing was checked.
- **Keyword / stop-phrase check** — per site: alert when a phrase disappears from the page, or when a bad one appears («Fatal error»). Case-insensitive, searched in the first 1 MB of the response both in the source and in the visible text as a visitor reads it (`&nbsp;`, `&laquo;` or a `<b>` inside the phrase do not get in the way). When you type a phrase the bot checks it against the page right away, with the same request the monitor makes: a phrase that is not there (or a stop phrase that already is) is not saved — send another one, or «💾 Сохранить всё равно» when the site really is broken right now. HEAD never downloads the page, so a phrase is neither checked nor accepted on a HEAD site, and HEAD cannot be chosen while a phrase is set. Catches the classic "HTTP 200 with a white screen".
- **Custom HTTP requests** — per site: method (GET/HEAD/POST…), headers (`Authorization: Bearer …`) and a request body (a JSON body goes out as `application/json` unless you set the header), so an API behind a token or a POST-only health endpoint is a first-class monitor. A check with its own headers or body never leaves for another origin: its redirects are followed only within the same server (same host and port; http→https is fine, https→http is not), and a redirect to another host is an alert — «API перенаправляет на … — ключ туда не отправляю» — rather than the key sent there.
- **Where the bot connects** (`utils/net.py`) — a monitor is checked where it points: a NAS or a service in the LAN is a legitimate monitor. Whatever other people wrote — the links on a page, nested sitemaps, the redirects of a public site, the image URL from the screenshot service — leads only to the public internet, never into the bot's own network (127.0.0.1, 10.x, 192.168.x, 169.254.169.254, the bot's own port). Such a link is not counted as broken; such a redirect is «🔴 … адрес во внутренней сети — туда не хожу». The resolved address is what is judged, so names, spellings like `0x7f.1` and DNS rebinding are closed by one rule; any IPv4 spelling is normalised when a site is added. `ALLOW_PRIVATE_TARGETS=0` is the strict mode for watching other people's sites: internal addresses cannot be added, and a monitor's name that points inside is not checked.
- **API checks — watch what the site actually does**: `POST https://good-pass.pages.dev/api/v1/analyze` with a JSON body, expecting `scoreLabel` in the answer; `GET …/api/whoami`. One rule (`utils/urls.py`, `is_api_check`): an http(s) monitor is an API check when its method is not GET/HEAD, **or** its path is `/api` or under `/api/`, **or** its host is `api.…`. An API check gets availability only — status code, the phrase in the response, response time, fail threshold and anti-flap — and no SEO audit, link crawl, sitemap 5xx sampling, page meta, AI-crawler probes, screenshot or regional timing (a GET to a POST endpoint is a 405, not an outage). Certificate, domain and DNS are checked once per host: when a regular site lives on the same host, the API check has none of its own (one alert, not two) and its card points to the site's card. The external second opinion (check-host sends a bare GET) is asked only for GET/HEAD requests without custom headers. An `/api/` address keeps its path and query when added; the card says «🔌 API-проверка: POST, …», the status page shows only its host with an API tag — never the path or the query (paths carry tokens too).
- **TCP and ping monitors** — `tcp://mail.example.com:25`, `ping://10.0.0.1`: non-HTTP services (mail, SSH, databases) get the same incident pipeline, anti-flap and external second opinion.
- **Bot-host health** — disk usage and docker containers on the server the bot runs on.

### 🔍 SEO / GEO (AI visibility)
- **noindex detector** — the classic silent killer: one bad deploy ships `<meta name="robots" content="noindex">` to production and you find out a month later from your traffic graph. The bot finds out the same day and bypasses all mutes. The homepage is what was asked for, not where it landed: a site answering `/` with a redirect to `/en/` that carries noindex is 🔴 «главная (→ /en/)», not a 🟠 inner page, and `/en/` from the sitemap is not read twice. Every form counts — `NAME="ROBOTS"` in any case, a second meta robots, meta googlebot and yandex, `content="none"`; `X-Robots-Tag` is read line by line and per crawler: `googlebot: noindex` is ours, `GPTBot: noindex` (AI only) does not ring, `max-snippet` / `unavailable_after` are not crawler names.
- **robots.txt** — blocking Googlebot/YandexBot is critical; blocking GPTBot/ClaudeBot/PerplexityBot is a warning (you *want* AI agents to see you). The file is read by the bot's own RFC 9309 parser (longest match wins, a tie goes to Allow, the crawler's own group beats `*`, `YandexBot` beats `Yandex`, a leading BOM is fine), so the verdict does not depend on the Python version and `Crawl-delay: ²` does not crash the audit.
- **An incomplete audit closes nothing** — when robots.txt answers 5xx/429 or not at all, or the homepage could not be parsed, the audit has no verdict: it neither closes nor lowers an open 🔴 (no "✅ nothing blocks search engines" in the morning and no repeated call while the ban stays), but may open or raise on what it did see (robots.txt 503 → 🟠 "robots.txt answers with an error"). The search screen says «⚠️ Часть проверки не удалась … — вердикта нет», and the snapshot never shows a level below the open incident. When a 🔴 becomes a 🟠 the owner hears «✅ запрет для поисковиков снят», not "all good".
- **Sitemap** — "no sitemap" only when the site said so: a 404/410, or something at sitemap.xml that is not a sitemap (an SPA's index.html, an empty `<urlset/>`); a timeout or a 5xx is not a finding. A map whose every address leads to another host (the old domain after a move) is its own 🟠 «карта сайта ведёт на другой адрес» with steps. A `sitemap.xml.gz` served without Content-Encoding is read.
- **A request signed as an AI crawler** — the homepage is asked again with the GPTBot, ClaudeBot and PerplexityBot signatures. When the plain request passed and a signed one gets 401/402/403/451, that is a block by signature, and the real crawlers send the same one. What this cannot see is a block by address: Cloudflare recognises the real AI crawlers by their IPs, and since July 2025 blocks them by default on new domains. So the finding says «a request with the signature», never «what GPTBot sees», and a clean Cloudflare site is not called «open to AI assistants» — the search screen says why and offers «💡 Проверить в Cloudflare» (AI Crawl Control → Crawlers); the site card carries a line and a button until opened once.
- **No-JS content measurement** — AI crawlers don't execute JavaScript. If your page is an SPA with 60 chars of text before JS runs, AI agents see a blank page — the bot will tell you. Pages are parsed in a separate process, so an audit of heavy pages (up to 2 MB) no longer stalls the bot: buttons, availability checks and `/health` keep answering, and the homepage is downloaded once per audit.
- Title/description (present, sane length), canonical target, h1, OpenGraph, lang, JSON-LD checks, soft-404 detection. Every finding is an action (🟠) with steps; nothing is listed just to say it is fine (no robots.txt, closed port 80, `llms.txt` present or not).
- **The screen says only what was measured**: «open to search engines and AI assistants» / «open, but N things in the way» / «🔴 closed to search». Whether the site is actually *in* an index only Search Console and Webmaster know — without them the screen says so and offers to connect them; with them it shows «📇 Google: homepage indexed (crawled 20.09)» from the daily index check, and marks data older than two days as «as of DD.MM».
- **Real index status** (optional): Google Search Console API (homepage dropped out of the index → critical alert; weekly clicks/impressions) and Yandex.Webmaster API (searchable pages, SQI, site problems — FATAL rings, CRITICAL waits for the morning). The Google verdict is what Google said: an answer without a verdict is «no verdict», never «removed from the index» (no alert). The state is kept per site, not per host, so the homepage and an inner page of it do not fight. The first observation is a quiet baseline (except FAIL: «🔴 Google не показывает … в поиске»); «🔴 Google убрал … из поиска» only when a PASS stopped being one; «✅ снова показывает» only after a 🔴 was said. Yandex problems are counted, not their kinds, and named in words: «1 критическая проблема и 2 серьёзные проблемы»; a mirror host never overwrites the main one, and one host whose summary failed does not lose the others.
- **External services that stopped working** (`services/integrations.py`, hourly job) — every call to Search Console, Webmaster, CrUX, GitHub, check-host.net, OSV and RDAP leaves a record (answered or not, and why — never an empty reason). A refused key or token (400/401/403), or a day without a single success, is said once: «🟠 Google Search Console: не работает — … Пока это не починить, …» with a «🔌 Проверить подключение» button; when it works again — one «✅ … снова работает». «⚙️ Настройки» shows «Google ⚠️ не отвечает» instead of «✅», the modules page says «⚠️ подключено, но не отвечает», the connections checklist marks the second opinion and the visitors' speed with ⚠️ and the reason. The Sunday report never drops a section silently: «⚠️ Google Search Console: не смог получить данные — …», «⚠️ Уязвимости: база OSV не ответила…», «⚠️ PR Dependabot: GitHub не ответил — список прошлой недели», «⚠️ GitHub: N репозиториев не прочитано». Only the sites the Search Console property covers are asked about; «with last week could not be compared» instead of «from zero». Visitors' speed data older than three days is dated on the card, and no incident opens or closes on stale numbers; a key the owner removed closes the open «visitors» incidents quietly.

### 🔧 Self-healing (Cloudflare Pages friendly)
- **The site card's picture** — once a day (with the morning audit) a screenshot of the page from the screenshot service is kept on the bot's disk, and Telegram draws it above the card's text. Only when there is somewhere to show it — the bot has a public address (`PUBLIC_BASE_URL`) — and never for an internal address: the service's free quota is not spent on pictures nobody sees. A refusal (HTTP 4xx, `status: fail`) is not asked four times, a failed picture is retried no sooner than 6 hours later rather than at every look at the card, and while one is being taken no second one starts for the same site.
- Alerts come with **one-tap action buttons**: re-check, trigger a Pages deploy hook, purge the Cloudflare cache, grab a live page screenshot.
- **Auto-redeploy**: fires the deploy hook itself when a site goes down (on by default once a hook exists): at most once an hour per hook (a Pages project), never for a site on pause or in a maintenance window, and reports in the alert what it did — or why it did not. Everything the bot does by itself (rebuilds, container restarts, docker cleanup) is visible and switchable in the chat: ⚙️ Settings → 🔌 Connections → «🤖 Что бот делает сам» — a switch per action, one pause for all of them (also «⏸ Не чинить самому 2 ч» right under the alert) and a journal of the last actions; the switch in the chat wins over `.env`. «🚀» and «🧹» under an alert ask for a confirmation first (it lives 10 minutes, a second «Да» starts nothing), and «🧹» purges the cache of the site's host only, not the whole zone.
- **Follow-ups without you**: 2 and 5 minutes after a "site down" alert the bot re-checks and edits the same message — "still down" or "already up". A "I'm on it, one hour of silence" button lives in every alert. A message about several sites gets one edit for all of them: "already up: …; still down: …".
- **Knows your hosting**: guesses Cloudflare / Vercel / Netlify / GitHub Pages / Railway / Render / Fly / Heroku from response headers and puts an "Open the panel" link into the alert; domain alerts link to the registrar's panel (Cloudflare, reg.ru, Namecheap, GoDaddy…).
- **Container auto-restart** (`AUTORESTART_CONTAINERS`) and **opt-in disk auto-cleanup** (`AUTO_CLEANUP=1`: dangling images and build cache older than a day, at most every 12 h, with a report of what was removed) — both need the docker socket mounted, which is root-equivalent access to the host. A stopped or unhealthy container is restarted and given its own healthcheck window to come up («health: starting» is waited out, not judged); at most 3 restarts per episode, with 10- and 20-minute gaps, then one «I am leaving it to you» message and the container is yours until it has been healthy for half an hour, which re-arms the alert and the budget (a «✅ back up» comes after a fix by hand, too). The bot never restarts its own container, even when it is listed. A container that is not in Docker (a typo, renamed, removed) and a Docker that stopped answering on the socket are said once (🟠) instead of silently switching the feature off; so is `AUTORESTART_CONTAINERS` set without the socket mounted.

### 📱 Managed entirely from the chat
- **Three buttons under the input field, no ☰ menu**: «🏠 Главная», «📖 Что я умею» (every function as «what it does → what you get», plus what each optional connection gives and who needs it) and «❓ Значки». A tap aborts any pending input.
- **One set of rules for the main screen and the site card**: status icons only (✅ 🟠 🔴 ⚠️ ⏳); one check time, at the top, as a time («проверено в 17:33»); a line is status · what · one number (the answer time «0.31 с», never «быстро»); a problem is said once, on the line of what it belongs to (mail by domain, in a «Почта» block); a block title carries only what its lines do not. The card puts problems first, then blocks by importance — availability (each sitemap page with its own mark), domain, mail and protection, search.
- **Everything watched, on one screen.** The main screen answers "is everything OK?" by itself — one line per site from the last checks, a «⏰ Задачи и боты» block with every heartbeat job (last mark, or how long it has been silent), open problems listed inline with their level — and every line has its own button straight to its card. Below: «🔎 Проверить всё сейчас», «➕ Добавить» (a site; an API, port or ping; a bot or scheduled job) and «⚙️ Настройки». «Проблемы» comes first and only while something is open, with the worst open level as its icon. A site card holds everything about one site at once (availability, certificate, domain, links, search and AI, downtime, its problems with "what to do") plus «🔧 Я чиню», «🔎 Поиск и ИИ», «🔗 Ссылки» and the site's settings. Settings hold only what is not "is it OK": digests and quiet hours, mute, maintenance windows, timezone, diagnostics and connections (with the test alert), status page, feedback, export/import.
- **One level dictionary** (`services/humanize.py`), the same in an alert, on the problems screen, in the menu, on the card and in the digests: 🔴 — act now (rings, bypasses mute and quiet hours); 🟠 — act, but not today (silent, listed in problems, on the card and in the digests); ✅ — back to normal; ⚠️ — could not check; ℹ️ — a fact that is not a problem. Facts of normal operation («3 pages checked», «certificate renewed by itself») are captions and digest lines — never counted, never alerted, never given a «what to do» button. The icon in the text always matches the delivery.
- **The problems screen**: its title and its menu button take the worst open level, every line has its own icon and number, and a «ℹ️ N» button for each problem (four in a row — the seventh and the twentieth too) opens in place what it means for visitors, what it usually is and the steps (with a button to the screen where it is fixed), plus «🔧 Я чиню» and «✓ Закрыть». Incidents of removed sites are not listed, and a check that started before a site was removed does not open one for it.
- **✓ Closing an incident** does not lie: for a site that is down, «✓ Закрыть» first checks it live and, if it still does not open, does not close it («🔴 Не закрываю: … всё ещё не открывается») — otherwise the next check would open it again with a ring and one more rebuild; «🔧 Я чиню» is the way to make the bot keep quiet. «🗑 Закрыть все» asks first (the confirmation lives 10 minutes), checks the sites that are down the same way and keeps them on the list. A certificate or domain warning closed by hand comes back on the next check if the date is still inside the band, a closed «медленно» after a new streak of slow answers.
- **Zero-config onboarding** — the first user to `/start` becomes the admin; an empty bot walks you through adding your first site and checks it immediately.
- **Sites** — add from the main screen («➕ Добавить»), remove from the site's card, with instant first-check feedback: the bot also suggests a phrase from the page to watch (catches "HTTP 200 with a blank page") and warns when the www twin behaves like a separate site. International names (`пример.рф`, `café.example.com`) are accepted and shown as written, stored and checked as `xn--…` (the same IDNA rules aiohttp uses); an IPv6 address for `tcp://`/`ping://` goes in brackets (`tcp://[2001:db8::1]:22`); only the scheme's own default port is dropped (`http://host:443` keeps its port). Only an `https://` site has a certificate: an `http://` one gets no certificate line on its card, the main screen or the add reply (the domain expiry is still checked). Removing a site is soft — its check and incident history stays, open incidents are closed — but its settings (phrase, method, headers, thresholds), the «🔧 Я чиню» pause, the SSL/domain alert ladders and the card snapshot are reset, so an address added again starts from a clean sheet (the confirmation screen says so). The 20-site limit holds on every way in («➕», «🛠 API, порт или ping» and the typed address; an address already watched is not a 21st). The DB is the source of truth; `.env` is just an optional first-run seed.
- **Two-level settings** — how often to check and whether to watch a phrase, in words; the other eight dials are behind «🛠 Для продвинутых».
- **⚙️ Settings** — morning report hour, evening report on/off, weekly report hour, quiet-hours presets: changed from the chat, applied to the running scheduler on the fly.
- **⚙️ Per-site overrides** — check interval, consecutive-failure threshold, accepted HTTP codes (e.g. `200-399,401`), keyword, "slow" threshold, HTTP method/headers/body — each site gets its own dials.
- **💾 Backups under the hood** — a nightly copy of the database on the server; on Sundays and on demand («🤖 Боты» → «💾 Скачать копию базы») a copy without connection tokens, secrets, API-check headers/bodies and visitors' IPs goes to the owner's private chat — never to a group (switch it off in «🔔 Когда писать»). To restore, send that file back: the bot recognises its copy (and older JSON exports) and asks before replacing anything; the tokens and API-check headers the copy lacks stay as they are on the same server, and are typed in again on a new one.
- **👀 Acknowledge** — «Знаю, не напоминать» on an escalation reminder: no more reminders about this incident, the next message about the site is «✅ поднялся»; the incident stays open, the checks go on, the site is not paused. «🔧 Я чиню» does the same for an hour.
- **🔧 Maintenance windows** — recurring schedules («weekdays 02:00–04:00», overnight windows welcome) per site or for everything: alerts and escalation stay silent, checks and stats keep running.
- **⏰ Tasks and bots (heartbeats)** — added from the chat («➕ Добавить» → «⏰ Бот или задача по расписанию») with a ready-to-paste `curl` line for your cron, or the same URL as another bot's healthcheck link; each job has an address of its own, shown on its card («🔗 Как подключена»), and each one sits on the main screen next to the sites.
- **⏸ Per-site pause** — deploying something big? Pause alerts for 1h or until morning; checks keep running silently. A problem that outlives the pause is said after it; a «✅ back up» about a fall the bot already reported comes through the pause and lifts «🔧 Я чиню».
- **🌐 Public status page** — publishing asks first: the bot shows what becomes visible to everyone (which sites, what about them) and offers to enable it with a secret link or open. Then an Uptime-Kuma-style page at `/status`: current state as the bot's verdict, not one raw check («down since HH:MM» only with an open incident, one failed check is «re-checking» without a red banner, another open incident is «degraded», stopped checks are «no fresh data» rather than all green, a new site shows «—» rather than a red 0%), 24h/7d/30d/90d uptime, anonymised incident history of known types only, maintenance banner. Only hosts are published — a web page's host, «host · API» without the path; tcp/ping monitors, ports and internal addresses never appear. A `/status.json` twin for your own dashboards carries `version` (now `1`) and `status` in `up` / `down` / `degraded` / `stale` / `maintenance` plus ISO timestamps and minute counts. SVG uptime badges for your README live at `/badge/<id>-<key>.svg` — their own key, no page slug in the address (the old `/status/badge/…` addresses still work for now and will be removed in a later release: replace them, then issue a new secret link). Built once at a time under a burst of hits. Off by default; an optional secret slug makes the URL private-by-obscurity, and switching it off or issuing a new one asks first.
- **⚙️ Settings in five questions** — when to write (digests, quiet hours, mute, maintenance windows, the test alert), helpers, connections (what is broken first with its fix, then what works and what could be added), what visitors see (status page, feedback widget), timezone.
- **🔔 Test alert** — arrives a minute after the tap (Telegram hushes the phone while you are in the app), rings like a real «site down», and «🔕 No» says what to fix.

### 💓 Dead-man switch
Your backup cron can't tell you it *didn't* run. Add a job in the chat («➕ Добавить» → «⏰ Бот или задача по расписанию») — the bot hands you the exact line for your cron:

```bash
curl -fsS https://your-server:8080/api/heartbeat/<job token>/backup
```

…and the bot alerts you when the job goes silent longer than its interval. Recovery is announced automatically. The token is the job's own (derived from `HEARTBEAT_SECRET`; rotating the secret changes every job's address), so one leaked cron line exposes one job, not all of them. `HEAD` is not a mark (link previews send it) — `405`; a name the bot does not wait for is `404`, so a typo in the cron line fails right there. Old addresses with the shared secret keep working, but the bot asks once per job to move it to its own address. Silence is counted from the last mark or from when the job was added, minus the bot's own downtime: neither a freshly added job nor a redeploy produces a false «молчит».

### 📊 Reports that respect your attention
- **Morning digest** — one message: per-site status, open problems, 7-day downtime (one phrase when the week was clean), upcoming SSL/domain expirations, disk, and right under the sites a line per bot or scheduled task (✅ works, with its expected rhythm; a silent one brings «connect / delete» buttons) and one for the bot's own watchdog — ✅ only while it actually takes the marks, and a search/AI line that never repeats an open problem. Reads in 10 seconds.
- **Weekly report** (Sundays) — downtime in minutes for the week and the month (raw checks + nightly rollups, so it stays honest past retention), everything open right now with its level (however old) and what was solved this week, certificates that renewed by themselves, an ASCII response-time chart (monospace, zero image libraries), Google/Yandex search metrics week-over-week, the state of the bot's own dependencies, GitHub hygiene — and exactly one suggestion with a button, never more. A long report is split into several messages, never cut.
- **GitHub hygiene** (optional: `GITHUB_TOKEN`, or «⚙️ Настройки → 🔌 Подключения → 🐙 GitHub») — a section of the Sunday report. One GraphQL query over the owner's repositories (`GITHUB_OWNER`, defaults to the token's account) and only what needs a hand: repositories gone since last week (the list is kept in the DB), open PRs older than 7 days, extra branches (not the default, not an open PR's head; `gh-pages` is fine), «Automatically delete head branches» switched off, a red CI on the default branch's latest commit, open Dependabot alerts when the token may read them. Archived repos and forks are watched for disappearance only. All tidy — no section at all; GitHub down or the token rejected — one «⚠️ не смог проверить» line, and the report arrives as usual. The bot's own Dependabot PRs are not repeated: the dependency line already names them.
- **Quiet first day** — a freshly added site is audited silently; its first SEO findings arrive in the next morning digest instead of ten separate alerts. Only findings that take the site out of search are ever alerted; the rest waits in «🔎 Поиск и ИИ» with a button per finding.
- **Quiet hours** — non-critical alerts queue up overnight and arrive as one morning digest. "Site down" always gets through.
- **Silent delivery** — informational messages arrive without a sound; only critical alerts ring. Silence-by-default, literally.
- **Escalation** — a site that is still down re-alerts with a growing pause: after 30 → 60 → 120 → 240 minutes, then every 4 hours (in quiet hours not more often than every 2 hours), and ignores mute; the helpers get the first reminder only. The first line says how long it has been down and why, the check interval in the text is the real one. A flapping site gets the hourly 🟠 instead, and a site that answered in its last planned check is not reminded about — its ✅ is a check away. A dead site must not be forgettable (deliberately availability-only: pages about an expiring cert would train you to ignore alerts). Three or more sites due for a reminder are one message, «🔴 Всё ещё не открываются N сайтов» with «🔧 Я чиню все»; the helpers get it when it is the first reminder for any of the sites.
- **Post-incident summaries** — recovery messages include duration and cause: *"✅ Recovered · down 12 min (14:03–14:15) · cause: HTTP 502"*.

### 🧹 It maintains itself
- Old raw checks roll up into daily aggregates nightly — the SQLite DB stays small forever. The same night removes what nothing reads any more: widget feedback (with the visitor's IP and User-Agent) is kept for 90 days, resolved incidents for a year, daily aggregates for 400 days. The quiet-hours / mute queue holds the newest 200 messages (critical ones are never queued); the morning digest says how many older ones did not fit. A check's history row, the card snapshot and the hosting are written in one transaction — one disk write per check instead of three.
- Nightly DB backups with rotation (written atomically, checked before they replace the previous copy, mode 0600) + a weekly off-host copy without tokens and secrets sent to the owner's private Telegram chat.
- **👥 Helpers** — up to three people who also get «site down», the first reminder about a site still down and «back up» — and nothing else (no certificates, domain, security or server news): the owner on holiday or with a dead phone no longer means nobody knows. The copy is text without buttons, signed «a copy for a helper»; the site is named the way the status page names it (the host, no path or port — tokens and internal addresses live there). The owner's mute and quiet hours do not hold the copy back; with «ring only when a site is down» the recovery reaches a helper silently. A one-off invite link that lives a day: a second look at the screen shows the same link (a new one is a separate button), and two people opening it at once do not both get in. A helper cannot steer the bot and leaves with /stop; the owner removes one after a confirmation.
- **Silence never lies.** The bot is quiet when all is well, so it makes sure quiet means nothing else: a message Telegram did not take is kept and retried every minute with a «⏳ Задержалось с 14:03» (delayed since 14:03) note; if more than 50 messages pile up during an outage, non-critical ones are dropped first and the bot says how many were lost; a failure on the bot's side is never a site's failure: before calling an unanswered site down the bot checks its own network (the `NET_CANARIES` hosts, or any site that just answered) — no network means no alerts, no downtime in the statistics, «no fresh data» on the status page and one summary for the whole episode once it is back, and a `ping://` monitor the bot may not open an ICMP socket for is one quiet «cannot check», not a 🔴 with escalation; after a restart following more than 10 minutes away it says when it was gone and how the sites are now, and sends a morning report that fell into the gap late; after the first site it offers a test alert (a minute later, so Telegram does not hush the phone while you are in the app) and the external watchdog. On Railway it also asks about the plan: the trial lasts 30 days, then the Free plan gives $1 a month while the bot needs about $2 (~190 MB of memory at $10 per GB-month), so without Hobby it would stop without a word. The question comes among the first steps, once more around day 25 after /start, and as a line in «🔌 Подключения» until the trial is over; «✅ Уже на Hobby» ends it. Installs from before this check get no reminder.
- **Telegram through a proxy** — `TELEGRAM_PROXY=socks5://user:password@host:1080` (or `socks4://`, `http://`) sends every call to Telegram through it, with api.telegram.org resolved on the proxy side — for a server that cannot reach Telegram directly (a VPS in Russia). Site checks go direct. A malformed value stops the start with a sentence; the password never reaches a log or the connections screen.
- **The database stays on disk.** On Railway without a volume the database is wiped on every deploy — with weekly auto-updates the bot would forget its sites and owner every week. It checks that the file sits on the volume and says so right after /start, on every start and in the diagnostics. Dependabot PRs merge only after the auto-merge job has seen every test job green — no branch rule needed in a fork.
- Self-heartbeat to an external watchdog (healthchecks.io) — who watches the watchman. The bot reads the answer, not only the status code (healthchecks.io says «OK (not found)» with HTTP 200 for a deleted check), shows the watchdog on the main screen and in the digest, and says once if it has refused the marks for half an hour. Marks are sent only while the checks run and Telegram answers, so the watchdog also catches a stuck bot, a dead Telegram channel or a bot that can no longer write to its owner.
- **Keeps its dependencies fresh without you**: Dependabot opens a weekly PR, CI (ruff + pytest + pip-audit) tests it, the auto-merge workflow merges patch and minor updates of the Python libraries released at least a week ago (a new base image — the Python version — and the Actions are merged by you), the host redeploys — and the bot announces «🔄 Бот обновился: aiohttp 3.10 → 3.14» on its next start, only when Python or package versions changed (direct dependencies by name, the rest as one «и ещё N» line); a new build with the same versions is a log line, the build number stays in «🩺 Диагностика». A newer version on PyPI is therefore not news; the bot reports only what needs a human — vulnerable packages (OSV checks every installed package, transitive yarl, multidict, certifi included), PRs that will not merge by themselves (a major bump, also inside the weekly group PR by its «Updates `x` from A to B» text, or a base image), minor PRs stuck for over two days (red CI) — and, hourly, a newest commit that failed to deploy while the bot still runs the old build. The repository comes from `GITHUB_REPOSITORY` (Railway and GitHub Actions set it themselves); on your own Docker server set it, or the deploy check and the PR list stay off and the log says so once after start. CI also builds the Docker image, but base-image bumps are never auto-merged: CI does not run the tests on the new Python. Every green `main` publishes `ghcr.io/morgunovtech/tofs_devops_bot` (`:latest` and `:sha-…`, amd64 and arm64) — nobody builds it by hand. The auto-merge dispatches CI on `main` itself, because a merge made with GITHUB_TOKEN starts no workflow run.
- **No volleys at outside services** — the jobs that call free third-party services (check-host, screenshots, GSC/Yandex, RDAP, CrUX) start 0–2 minutes after their minute, so installations in one timezone do not knock at the same second. The digests, retention and the backup keep their minute, as promised.
- Secrets take care of themselves: an empty or placeholder `WEBHOOK_SECRET`/`HEARTBEAT_SECRET` is replaced by a generated one stored in the DB. The two are always different — the webhook secret is public by design (it ships in the widget), the heartbeat one is not. A heartbeat is accepted only with the job's own token (derived from the heartbeat secret) or the old shared heartbeat secret, never the webhook one.

### 📩 Bonus: feedback widget
A tiny embeddable JS widget for your sites — messages are stored in the bot («🔌 Подключения» → «📩 Обратная связь») and land in your Telegram with the visitor's text as a quote, so it cannot draw lines that look like the bot's own. Server-side: CORS only for the sites added to the bot (www. and subdomains count), separate rate limits per address and per site, size caps, and a budget of 5 chat messages per hour per site — the rest is stored and summed up in one quiet hourly message with a button to the list. Two modes: a floating "⚠️ Проблема?" button, or `button: false` plus `data-devops-feedback` on any link — the classic footer "нашли опечатку?" opens the form with the visitor's selected text pre-filled. The snippet from the bot loads the widget only after the page has loaded and pins the file by its hash (SRI): a hung bot host cannot stall the site, and a tampered file is refused by the browser; after an update that changed the file the bot asks for the new snippet. Settings are also read from `data-*` attributes, so a copy of the file on the site works under a strict CSP without inline scripts. The page address is sent without its query or fragment (`fullUrl` sends it whole), the User-Agent is not stored, and the visitor sees under the field that the page address and their IP go along with the message. Setup snippet and the CSP notes: [docs/SETUP.md](docs/SETUP.md#виджет-обратной-связи-нашли-опечатку).

## Quick start

### Railway (no server needed)

Fork this repo → [Railway](https://railway.com) → **New Project → Deploy from GitHub repo**. Railway picks up the `Dockerfile`; then:

1. **Variables**: `TELEGRAM_BOT_TOKEN` (from [@BotFather](https://t.me/BotFather)) and `DB_PATH=/app/data/bot.db`. Secrets are generated on first start.
2. **Attach Volume** at mount path `/app/data` — the SQLite DB must survive redeploys.
3. **Settings → Networking → Generate Domain** (port **8080**), then set `PUBLIC_BASE_URL=https://<your-app>.up.railway.app`.

Full click-by-click walkthrough in plain language (RU): [docs/SETUP.md](docs/SETUP.md).
Note: the docker-socket features (container auto-restart, disk auto-cleanup) only apply to self-hosting; on Railway they are simply off. If `AUTORESTART_CONTAINERS` is set but the socket is not mounted, the bot says so (🟠) instead of staying quiet.

### Self-hosted (Docker Compose)

walks you through adding your first site. Sites, report hours, quiet hours

## Architecture

```
main.py                 entry point: DB → services → web server → scheduler → polling
├── monitors/           availability, ssl, domain (rdap), dns, links, deep 5xx,
│                       seo/geo, host — typed results, shared alert ladder
├── services/           notifier (the one door for every message: priorities,
│                       mute, quiet hours, pauses), settings, maintenance,
│                       secrets, runtime (admin), updates (dependency watch),
│                       cloudflare actions, docker API, screenshots, GSC, Yandex,
│                       GitHub hygiene
├── reports/            scheduler (19 jobs), formatters, ASCII weekly report
├── handlers/           one router per screen behind a single AdminFilter
├── web/                aiohttp: feedback API, heartbeats, status page + JSON
│                       + badges, the widget; HTML template in web/templates
├── db/                 aiosqlite, WAL, PRAGMA user_version migrations,
│                       retention rollups, backups
├── utils/              url/text/time helpers shared by everything above
└── tests/              pytest: pure functions, DB, monitors against a local
                        HTTP server, notifier rules, web endpoints, bot screens
```

Stack: Python 3.12+, [aiogram 3](https://github.com/aiogram/aiogram), aiohttp, APScheduler, SQLite (WAL), stdlib `zoneinfo`. No external monitoring dependencies — the bot *is* the monitoring. No image libraries either: charts are monospace text.

A note on the feedback widget's security model: the widget's "secret" ships to every site visitor, so the endpoint is treated as public — protection is CORS limited to the monitored sites, rate limits per address and per site, strict size caps and a per-site budget of chat messages (at most 5 an hour, the rest summed up hourly), not the token. That is exactly why the heartbeat endpoint uses a *different* secret. A deliberate, documented trade-off for a personal-scale tool.

## Development

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
pip install --require-hashes --no-deps -r requirements.txt   # exactly what the image gets
ruff check .          # lint + import order
pytest -q             # ~150 tests, no network, no Telegram
pip-audit -r requirements.txt --strict
```

Direct versions live in `requirements.in`; `requirements.txt` is the lock
generated from it (every package, transitive ones included, with hashes;
compiled under Python 3.12). After changing a pin, regenerate it with
`pip-compile --generate-hashes --strip-extras --output-file=requirements.txt requirements.in`
(pip-tools) — the weekly Dependabot PR does this itself.

CI (ruff, pytest on Python 3.12, 3.13 and 3.14, `pip-audit --strict`, the image build on the 3.13 leg) runs on every PR and on every push to `main`; a green `main` publishes the image to ghcr.io. Dependabot files one grouped PR for the Python libraries every Saturday at 13:00 (Europe/Moscow) and monthly PRs for the base image and the Actions; a version reaches a PR no sooner than 7 days after its release (a major one — 30). The auto-merge waits for every «lint · test · audit» check itself and merges only patch and minor updates of the Python libraries — exactly the commit the tests checked; the base image, the Actions and major versions wait for a human. Nothing has to be configured in the repository; if you want a branch rule, require «lint · test · audit (3.12)», «(3.13)» and «(3.14)». The container runs as an unprivileged user; `entrypoint.sh` fixes the data volume's ownership first.
